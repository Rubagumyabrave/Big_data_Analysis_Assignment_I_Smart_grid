## 3.3 Explaining the chunk results

Evidence: chunk counts and boundaries (3.1), medians (3.2), EXPLAIN (ANALYZE, BUFFERS) plans.

| Query | Chunks scanned 3h / 1d / 7d | Planning time 3h / 1d / 7d (ms) |
|---|---|---|
| Q1 | 9 / 2 / 1 | 0.77 / 0.48 / 0.43 |
| Q2 | 57 / 8 / 2 | 2.29 / 0.60 / 0.69 |
| Q3 | 225 / 29 / 5 | 7.90 / 0.99 / 0.85 |
| Q4 | 57 / 8 / 2 | 2.20 / 0.55 / 0.67 |
| Q5 | 225 / 29 / 5 | 6.35 / 0.91 / 0.38 |

**Q1: fastest 3 hours (117.8 ms vs 122.2 for 1 day, 18 % faster than 142.9 for 7 days).**
Observation: 7 of the 9 three-hour chunks lie entirely inside 21 September and are read by sequential
scan with no filter; the 1-day table reads one chunk by index and one by sequential scan with a filter
(daily chunks run 02:00-02:00 CAT, so 22 Sep 00:00-02:00 rows are removed); the 7-day table must
index-scan about 380,000 rows inside one 2.6 M-row chunk and then sort.
Explanation: when chunks fit inside the time window, whole chunks are read cheaply; large chunks force
an index search inside the chunk.

**Q2: fastest 1 day (278.4 ms vs 285.9 for 3 hours and 325.2 for 7 days, 14 % slower).**
Observation: 57 / 8 / 2 chunks; the Tuesday-Monday week does not align with Thursday-Thursday weekly
chunks, so the 7-day table searches inside two large chunks; the 3-hour table has the highest planning
time (2.3 ms).
Explanation: daily chunks match the week closely without creating many chunks to plan and open.

**Q3: fastest 7 days (1270.9 ms), tied with 1 day (1275.6 ms); 3 hours is 1.88x slower (2393.1 ms).**
Observation: the 3-hour plan uses a plain Append with no Gather (no parallel workers) and a separate
partial aggregate per chunk (225 x 4,000 = 900,000 partial rows to merge); planning 7.9 ms. The
1-day and 7-day plans use Gather / Parallel Append with 2 workers.
Explanation: with 225 small chunks the planner chose per-chunk aggregation in a single process, so the
query used one CPU core instead of three and paid a large merge cost.

**Q4: fastest 7 days (2.8 ms vs 6.4 for 1 day and 6.9 for 3 hours, 2.3-2.5x faster).**
Observation: 2 / 8 / 57 chunks, each needing its own (meter_id, event_time) index lookup that returns
only about 12 rows per three-hour chunk; planning 2.2 ms for 3 hours.
Explanation: the per-chunk fixed cost (planning, opening, index descent) dominates when each chunk
contributes very few rows, so fewer chunks win.

**Q5: all within 4 % (902.4 / 940.4 / 929.1 ms); 3 hours nominally fastest.**
Observation: all configurations read every row (about 120,000 pages) with parallel sequential scans.
Explanation: the same amount of data must be read regardless of chunking; the difference is within
run-to-run variation (7-day max 1,084.9 ms).

**Conclusion:** 1-day chunks are never the slowest and are within 2 % of the best on four of five
queries. 3-hour chunks fail on whole-table grouping (Q3), and 7-day chunks are weakest on short time
windows (Q1, Q2). 1 day is the best all-round interval and is used for Section 4.

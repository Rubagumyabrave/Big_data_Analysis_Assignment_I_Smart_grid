# 7.4 Dashboard timing: Raw vs Aggregate

Script: src\dashboard_timing.py (Playwright driving the installed Chrome, headless, 1920x1400)
Range 2026-09-22 00:00 to 2026-09-29 00:00 CAT, $meter = 1000000000.

Test conditions
- TimescaleDB jobs 1000-1004 (2 compression, 3 continuous-aggregate refresh policies) paused
  before the test and resumed afterwards (scheduled = t, see 7.4_b_jobs_resumed.png).
- No writes: energy_readings = 10,643,735 rows before and after; 0 other active sessions.
- Browser cache disabled (Chrome DevTools Network.setCacheDisabled); Grafana OSS has no query cache.
- 1 warm-up + 10 measured refreshes per dashboard (Grafana Refresh button), alternating Raw and
  Aggregate so both saw the same machine conditions.
- Panel time = panel's /api/ds/query request sent -> response received.
  Dashboard time = Refresh click -> last panel's data received.

Interpretation
- The Aggregate dashboard loads in ~0.5 s instead of ~12.9 s (26.1x faster). The Raw dashboard
  time is set by its slowest panel (hourly regional, scan + JOIN with meters).
- Raw panel times are higher than the single-query benchmark in 3.2 because the five panels run
  concurrently and compete for the same 4 CPUs and disk, which is how a dashboard behaves in practice.
- The single-meter panel gains nothing (0.7x, ranges overlap): on the raw table it is an index
  lookup of ~672 rows (meter_id, event_time index), already at the ~100-250 ms floor of Grafana
  request overhead. Continuous aggregates pay off for panels that scan and group many rows,
  not for narrow indexed lookups.
- Aggregate panel times are dominated by fixed Grafana/browser overhead, not database work.

Costs of the continuous aggregates (from 6.1)

| Item | Value |
|---|---|
| Storage (3 aggregates) | 17.93 MB (vs 1,042.7 MB for the raw hypertable, about 1.7 %) |
| Initial full refresh (1-29 Sep) | 188.03 s (108.19 + 52.00 + 27.84) |
| Ongoing refresh | policies every 15 min over a 3-day window; last run durations: 15min __, hourly __, daily __ |

Trade-off: each Aggregate dashboard refresh saves about 12.4 s. The one-off 188 s initial
refresh is recovered after about 15 dashboard refreshes, and the 18 MB of storage is negligible.
The ongoing cost is the background policy runs, which happen off the user's critical path.

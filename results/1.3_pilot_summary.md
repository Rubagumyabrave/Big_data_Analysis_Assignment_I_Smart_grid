Run 2 included 6 deliberate generator duplicates (1,994 unique meter/time pairs), counted as separate messages and rows.

**Run 1 difference: 183 messages.** Publisher log: 2,000 taken and 2,000 acknowledged, no failures.
Subscriber log: 1,817 received, 0 redelivered, 0 parse errors, 0 insert errors. So the loss was inside
the broker. EMQX metrics confirm it: messages.received 2,000, messages.delivered 1,817,
delivery.dropped.queue_full 183, messages.dropped.no_subscriber 0. The publisher sent 2,000 messages
in 1.70 s (≈1,200 msg/s) while the subscriber inserted batches inside the MQTT callback, blocking
message reading. The subscriber's broker queue overflowed and EMQX discarded 183 QoS 1 messages.
A PUBACK only confirms receipt by the broker, not delivery to subscribers.

**Corrections:** (1) the subscriber now parses messages in the MQTT thread and inserts in a separate
database-writer thread via a queue, so message reading never waits for the database (max backlog
133 rows in run 2); (2) the publisher paces sending at 300 msg/s.

**Run 2:** 2,000 at every stage; EMQX delivery.dropped.queue_full unchanged at 183 (no new drops).
